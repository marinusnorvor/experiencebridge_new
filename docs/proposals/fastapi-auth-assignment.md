## Acceptance criteria — proposed Given / When / Then

1. **Registration and verification:** Given a new normalized email, when valid registration and a current verification token are submitted, then the user is uniquely created, verified once and can sign in. Concurrent duplicates do not create duplicate identities. Invalid, expired or reused tokens fail without disclosing secrets.
2. **Credentials and sessions:** Given a verified account, when correct credentials are supplied, then a rotated opaque HTTP-only cookie maps to a hashed, expiring Neon session; invalid credentials return a generic error and unverified users cannot enter protected portals. Expired and revoked sessions are rejected; logout revokes the record and clears the cookie across the chosen proxy.
3. **Recovery:** Given a recovery request, when an eligible user consumes an unexpired token once, then the password changes and all prior sessions are revoked. Unknown emails receive the same public response; expired and reused reset tokens fail.
4. **Existing users:** Given an eligible uniquely identifiable legacy user, when approved proof of email ownership completes, then password access attaches to the same internal ID without changing roles, memberships or business associations. Ambiguous or unverified records are held for approved manual resolution; email submission alone cannot link an account.
5. **Authorization and CSRF:** Given an authenticated user, when accessing a protected resource, then the backend checks active status, current role grants and contextual membership/assignment. Anonymous, unverified, forbidden and expired cases are handled appropriately; unsafe requests including login reject missing/invalid CSRF and disallowed origins. Registration never grants privileged roles.
6. **Abuse and deployment:** Given multiple application instances, when login or email-triggering requests exceed approved limits, then an atomic persistent limit applies. Production requires secure configuration, allowed origins and delivery; test transport does not send real email. No persistent auth state falls back to process memory or local files.
7. **Portal and contract compatibility:** Given a verified authorized actor, when each existing portal loads `/api/v1/me`, then the agreed UserSelf shape and server-authoritative contexts continue to work. Shared frontend operations handle loading, unauthenticated, forbidden, expired and unavailable states; safe redirects, credentialed requests and CSRF bootstrap work. Arena can use documented shared exports and screen files without implementing a second auth system.
8. **Verification and handoff:** Given verified Neon staging, when focused backend tests, client integration tests and frontend production build run, then results are recorded truthfully; browser end-to-end flow is tested if available using synthetic users and development mail. Review the full diff, migrations and remaining Clerk references; classify legacy references, remove runtime use only when safe, and record unrun or unrelated failures.
